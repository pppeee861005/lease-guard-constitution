# 🔄 Subagent 並行工作流設計

## 核心概念

**計劃14 採用「L1 Subagent 並行網路資料蒐集」工作流，這是一套可複用的方法論。**

適用場景：
- ✅ 官方資料結構化（政府公告、法規更新）
- ✅ 多來源交叉驗證（版本對照、內容核實）
- ✅ 版本管理與變更追蹤（105-114年歷史）
- ✅ 時效性資料快速蒐集（緊急法規通知）

## 計劃14 的三支 Subagent 執行

### 執行架構圖

```
任務分解 (Task Decomposition)
├─ L1-01: 行政院消費者保護會官文下載
│         + 內政部公報版本收集
│
├─ L1-02: 內政部契約範本蒐集
│         + 版本對應整理
│
└─ L1-03: 法規資料庫歷史追蹤
          + 版本修正時間線

          ⬇️ (並行執行，15分鐘完成)

資料整合 (Data Aggregation)
├─ 下載完成報告
├─ 下載網址表
└─ 版本對應分析

        ⬇️

核心洞察提煉 (Insight Extraction)
├─ 發現1：電費條款 5 年滯後風險
├─ 發現2：版本升級信息不透明
└─ 發現3：並行工作流 4-5x 加速潛力

        ⬇️

計劃14輸出 (Plan 14 Output)
├─ 租賃憲法撰寫指南 (8K 字)
├─ 電費條款修正草案 (6K 字)
├─ 版本追蹤總表 (5K 字)
├─ 法規監控與更新SOP (7K 字)
└─ 四蜂群執行成果報告
    (含 Token 消耗分析)
```

## 三支 Subagent 的詳細執行

### L1-01：官方原文下載與驗證

**目標**：取得 114年4月18日最新版本的官方規範

**任務清單**：
```
□ 前往行政院消費者保護會官網
  → 查詢「住宅租賃定型化契約應記載及不得記載事項」
  → 下載 114年4月18日 公告版本

□ 前往內政部地政司官網
  → 蒐集「住宅租賃契約書範本」
  → 確認 113年7月8日修正版本

□ 前往內政部全球資訊網
  → 查詢「行政院公報」相關公告
  → 記錄發布日期與版本號
```

**成果**：
- ✅ 114年4月18日官方公報（PDF）
- ✅ 113年7月8日合約範本（DOCX + ODT）
- ✅ 各版本之間的修正說明文件

**關鍵成功因素**：
1. **官方來源優先**：行政院 > 內政部 > 地方政府 > 民間組織
2. **版本號精確**：記錄完整的年月日（如 114/4/18）
3. **備份多格式**：PDF/DOCX/ODT 增加可用性

---

### L1-02：版本對應與範本整理

**目標**：整理 109年、113年、114年版本的對應關係

**任務清單**：
```
□ 從已蒐集的文件提取版本信息
  → 109年8月14日版本
  → 113年7月8日版本
  → 114年4月18日版本

□ 逐點對照三個版本
  → 標記出「新增」的條款
  → 標記出「修改」的條款
  → 標記出「刪除」的條款

□ 尤其關注以下條款的演變
  → 第6點（電費計費方式）
  → 第11點（資訊提供義務）
  → 第18點（承租人終止權）
```

**成果**：
- ✅ 版本對應分析報告（逐點對照）
- ✅ 修正說明與對照表
- ✅ 關鍵改動的深度解讀

**關鍵成功因素**：
1. **逐點追蹤**：不遺漏任何修改
2. **時間標記**：記錄何時發生修改
3. **實務影響分析**：說明修改對用戶的影響

---

### L1-03：法規資料庫與版本歷史

**目標**：建立 105-114年完整的版本歷史檔案

**任務清單**：
```
□ 前往「全國法規資料庫」(laws.moj.gov.tw)
  → 查詢「住宅租賃契約相關規定」
  → 提取每次修正的完整版本
  → 記錄修正日期

□ 搜尋歷年「行政院公報」
  → 找出 V1.0 (105年6月23日)
  → 找出 V2.0 (109年8月14日)
  → 找出 V3.0 (112年6月14日)
  → 找出 V4.0 (113年7月8日)
  → 找出 V5.0 (114年4月18日)

□ 對每個版本進行內容確認
  → 電費計費方式如何定義？
  → 有無資訊提供義務？
  → 終止權門檻是什麼？
```

**成果**：
- ✅ 版本追蹤總表（105-114年完整時間線）
- ✅ 版本升級路徑診斷工具（3步驟快速判定）
- ✅ 常見誤區警示（法規滯後性提醒）

**關鍵成功因素**：
1. **完整性**：不遺漏任何主要版本
2. **可追溯性**：每個版本都有時間戳
3. **診斷工具化**：幫助用戶快速判定自己的合約版本

## 工作流程的三個關鍵設計

### 1️⃣ 任務獨立性

```
獨立 ✅：
  - L1-01 下載官文
  - L1-02 整理範本
  - L1-03 追蹤版本

  → 三個任務可完全並行，零依賴

依賴 ❌：
  - L1-02 需要先 L1-01
  - L1-03 需要先 L1-01 & L1-02

  → 這種結構必須串列執行，無法並行
```

計劃14 之所以能 15 分鐘完成（而不是 60 分鐘），正因為三支任務完全獨立。

### 2️⃣ 資訊來源多元化

```
多層次驗證策略：

Level 1（官方來源）：✅ 最可信
  └─ 行政院消費者保護會
  └─ 內政部地政司
  └─ 行政院公報

Level 2（法規資料庫）：✅ 可信
  └─ 全國法規資料庫 (laws.moj.gov.tw)

Level 3（NGO + 社群）：⚠️ 參考
  └─ 崔媽媽基金會（合約範本解讀）
  └─ 法律扶助基金會（爭議案例）

交叉驗證：
  官方版本 ← → 法規資料庫版本 ← → NGO 版本

  三者完全一致 → 100% 確定
  兩者一致，一者有異議 → 調查異議原因
  三者有分歧 → 以官方最新公告為準
```

### 3️⃣ 結果聚合與提煉

```
原始資料（第一層）：
  30,000+ 字 + 5 份文檔

  ↓ 結構化處理

規範化內容（第二層）：
  版本對應表、條款詳解、歷史時間線

  ↓ 跨域分析

核心洞察（第三層）：✨
  發現1：電費條款 5 年滯後 → $2,400-6,000/年損失
  發現2：版本升級無通知機制 → 大量用戶仍在用舊版
  發現3：結構化與並行設計 → 計劃13 的工作流基礎
```

## 可複用的工作流範式

### 通用設計框架

```
Step 1：任務分解 (Decomposition)
  → 確認每個子任務的目標與交付
  → 檢查是否存在依賴關係
  → 設定清晰的成功標準

Step 2：平台分配 (Platform Assignment)
  → 每個任務分配給一個 Subagent
  → 提供清晰的指令與資源清單
  → 設定超時與失敗回退方案

Step 3：並行執行 (Parallel Execution)
  → 同時啟動所有獨立任務
  → 監控執行進度
  → 記錄執行時間

Step 4：結果聚合 (Aggregation)
  → 收集所有 Subagent 的輸出
  → 進行格式標準化
  → 去重與去衝突

Step 5：洞察提煉 (Extraction)
  → 從聚合結果尋找 Pattern
  → 建立結構化的輸出（指南、表格、工具）
  → 預留反饋迴圈的設計
```

### 計劃14 的具體應用

| Step | 計劃14 的執行 | 耗時 |
|------|----------|------|
| 1️⃣ 任務分解 | 確定三個 Subagent 任務 | 5分 |
| 2️⃣ 平台分配 | 分別指配下載、整理、追蹤 | 2分 |
| 3️⃣ 並行執行 | 三支 Subagent 同時執行 | 8分 |
| 4️⃣ 結果聚合 | 整合五份文檔與報告 | 2分 |
| 5️⃣ 洞察提煉 | 提煉三大核心發現 | 3分 |
| **總計** | | **20分** |

## 常見陷阱與避免方案

### ❌ 陷阱1：假獨立性

```
問題：
  L1-A 下載文件
  L1-B 依賴 L1-A 的輸出才能開始
  → 實際上仍是串列執行

解決：
  確保每個 Subagent 有獨立的信息來源
  L1-A 和 L1-B 分別訪問不同網站
  不依賴彼此的中間產物
```

### ❌ 陷阱2：來源單一化

```
問題：
  三支 Subagent 都去同一個官網
  → 浪費並行的優勢
  → 並發請求可能觸發 rate limit

解決：
  多元化信息來源
  官方 + 法規資料庫 + NGO 資源
  實現「交叉驗證」而非「重複驗證」
```

### ❌ 陷阱3：結果無法聚合

```
問題：
  L1-A 輸出：自由文本格式
  L1-B 輸出：結構化表格
  L1-C 輸出：URL 清單
  → 無法統一處理

解決：
  預先定義輸出格式（JSON / CSV / Markdown Table）
  在 Subagent 指令中明確說明格式要求
  使用轉換腳本統一格式
```

### ❌ 陷阱4：缺少反饋迴圈

```
問題：
  計劃14 蒐集完資料就結束
  計劃13 應用時發現規則漏報
  → 計劃14 無法更新

解決：
  設計「計劃13 → 計劃14」的反饋機制
  定期檢查「哪些規則在實戰中失效」
  回報給計劃14 進行源頭修正
```

## 建議的推廣方式

### 給新專案的三個起點

```
1️⃣ 評估是否適用
   問自己：我有 ≥3 個完全獨立的資料蒐集任務嗎？
   如是 → 適用此範式

2️⃣ 任務分解
   把大任務拆成 3-5 個獨立的小任務
   確保每個任務有清晰的輸入 & 輸出

3️⃣ 來源多元化
   不要讓所有 Subagent 去同一個地方
   官方 + 資料庫 + NGO + 社群 = 交叉驗證
```
